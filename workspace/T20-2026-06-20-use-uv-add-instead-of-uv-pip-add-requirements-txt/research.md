# Research Findings

Scope: build/dependency tooling — `Makefile`, `Justfile`, `.github/workflows/check.yml`,
and dependency config in `pyproject.toml` (`uv.lock`, `requirements.txt`, `requirements-dev.txt`).

## Q1: Which `uv` subcommands does each recipe invoke (env creation, install, sync, compile), with exact args and target files?

### Findings

**Makefile** (`Makefile`):
- `.venv` target (`Makefile:8-12`):
  - `pip install uv` — bootstraps uv via pip.
  - `uv venv -p $(PYTHON_VERSION) .venv` — creates the virtualenv; `PYTHON_VERSION ?= 3.11` (`Makefile:3`).
  - `uv pip sync requirements-dev.txt` — installs the pinned dev set.
  - `uv pip install -e .[test]` — editable install of the project plus the `test` extra.
- `sync` target (`Makefile:45-47`): repeats `uv pip sync requirements-dev.txt` + `uv pip install -e .[test]` (no `.venv` prerequisite, no venv creation).
- `compile` target (`Makefile:49-51`):
  - `uv pip compile -U -q --python 3.11 --no-strip-markers pyproject.toml -o requirements.txt`
  - `uv pip compile -U -q --all-extras --python 3.11 --no-strip-markers pyproject.toml -o requirements-dev.txt`
- Tool recipes (`test`, `lint`, `mypy`, `deadcode`, `format`, `audit`, `fixlint`, `publish`) invoke binaries directly from `.venv/bin/...` (e.g. `Makefile:21,24,30`), not via `uv run`.

**Justfile** (`Justfile`):
- `sync` recipe (`Justfile:6-8`): `uv pip sync requirements-dev.txt` then `uv pip install -e .[test]` (each line `@`-prefixed/quiet). No `uv venv` — relies on an ambient `.venv`.
- `lifecycle` recipe (`Justfile:1-4`): same two install lines, then a loop running `uv run lifecycle --max-tasks 1 --prior-tasks "$count"`.
- All other recipes depend on `sync` and execute tools via `uv run`: `uv run pytest` (`Justfile:11`), `uv run ruff format` (`:14`), `uv run ruff check` (`:17,26`), `uv run ruff check --select C901` (`:29`), `uv run mypy` (`:20,32`), `uv run ruff format --check` (`:23`).
- The Justfile has **no** `compile` recipe and **no** `uv venv` / `uv lock` invocation.

Neither file invokes `uv add`, `uv lock`, or `uv sync` (project mode). Only the `uv pip ...` (pip-interface) subcommands are used, plus `uv run`/`uv venv`.

## Q2: Relationship between `pyproject.toml`, `requirements.txt`, `requirements-dev.txt`, `uv.lock` — generation, consumers, sync

### Findings

- **`pyproject.toml` is the source of truth.** Runtime `dependencies = []` (`pyproject.toml:21`); the dev/test toolchain lives in `[project.optional-dependencies].test` (`pyproject.toml:23-34`: hatch, ruff, mypy, pip-audit, deadcode, pytest, pytest-cov, pytest-xdist, vupi).
- **`requirements.txt`** is auto-generated by `uv pip compile --python 3.11 --no-strip-markers pyproject.toml -o requirements.txt` (header `requirements.txt:1-2`). Since runtime deps are empty, the file has only the header (`requirements.txt:1-2`, no package lines).
- **`requirements-dev.txt`** is auto-generated by `uv pip compile --all-extras --python 3.11 --no-strip-markers pyproject.toml -o requirements-dev.txt` (header `requirements-dev.txt:1-2`); it contains the fully pinned, marker-annotated transitive set (`requirements-dev.txt:3+`).
- Both requirement files are (re)generated by `make compile` (`Makefile:49-51`).
- **Consumer of the requirement files:** only `requirements-dev.txt` is consumed — by `uv pip sync requirements-dev.txt` in both build runners (`Makefile:11,46`; `Justfile:2,7`). `requirements.txt` is generated but **not referenced** by any recipe or CI step (no consumer found in grep).
- **`uv.lock`** is a full uv project lockfile: `version = 1`, `revision = 3`, `requires-python = ">=3.11"` (`uv.lock:1-3`) with resolution-markers for 3.14/3.15 & win32/non-win32 (`uv.lock:4-10`). It is **not referenced by any recipe/CI command**; no `uv sync`/`uv lock` invocation exists in Makefile, Justfile, or CI. It is implicitly read only by `uv run` (Justfile recipes, `Justfile:11` etc.).
- **Staying in sync:** there is no automated cross-check. `make compile` regenerates the two requirements files together; `uv.lock` has no regenerating recipe (would require a manual `uv lock`). So `uv.lock` and `requirements-dev.txt` are independently maintained artifacts that can drift.

## Q3: How does GitHub Actions CI set up env and install deps, and which recipes/args does it use?

### Findings

- Workflow `.github/workflows/check.yml`, job `build`, `runs-on: ubuntu-latest` (`check.yml:13-15`).
- Matrix over Python `["3.11","3.12","3.13","3.14"]` (`check.yml:17-19`).
- Steps:
  - `actions/checkout@v4` (`check.yml:22`).
  - `actions/setup-python@v5` with `python-version: ${{ matrix.python-version }}` (`check.yml:23-26`).
  - Install: `make .venv PYTHON_VERSION=${{ matrix.python-version }}` (`check.yml:27-29`) — runs the Makefile `.venv` target (pip-install uv → `uv venv` → `uv pip sync requirements-dev.txt` → `uv pip install -e .[test]`).
  - Run checks: `make check` (`check.yml:30-32`) → `make check` = `test lint mypy audit deadcode` (`Makefile:5`).
- CI relies **only on the Makefile**, not the Justfile.

## Q4: How is the project's own package (editable install) and the `test` extras made available to test/lint/type-check/check recipes?

### Findings

- Editable + extras install happens via `uv pip install -e .[test]` in the `.venv`/`sync` recipes of both runners (`Makefile:12,47`; `Justfile:3,8`). This installs the `deadcode` package editable and pulls in `[project.optional-dependencies].test` (`pyproject.toml:23-34`).
- **Makefile path:** tool recipes shell out to `.venv/bin/<tool>` (e.g. `.venv/bin/pytest` `Makefile:21`, `.venv/bin/ruff` `:24`, `.venv/bin/mypy` `:30`, `.venv/bin/deadcode` `:33`, `.venv/bin/pip-audit` `:43`). Each depends on the `.venv` target (`Makefile:20,23,29,32,42`), which performs the editable+extras install. `check` aggregates `test lint mypy audit deadcode` (`Makefile:5`).
- **Justfile path:** every recipe depends on `sync` (`Justfile:10,13,16,19,22,25,28,31`) and runs tools through `uv run` (which resolves them in the synced environment). `check` aggregates `check-format check-lint check-complexity check-typecheck test` (`Justfile:34`).
- The `deadcode` console entry point is `deadcode.cli:main` (`pyproject.toml:36-37`), available after the editable install.

## Q5: What `uv`-related config in `pyproject.toml` affects resolution/installation/locking?

### Findings

- A custom index is declared: `[[tool.uv.index]]` named `gitlab`, url `https://gitlab.com/api/v4/projects/niekas%2Fpackages/packages/pypi/simple` (`pyproject.toml:48-50`).
- This index is the resolution source-of-record in the lockfile: packages carry `source = { registry = "https://gitlab.com/.../simple" }` (e.g. `uv.lock:15,24`), while wheel/sdist download URLs still point at `files.pythonhosted.org` (`uv.lock:16-18`).
- No other `[tool.uv]` keys (no `tool.uv.sources`, `index-strategy`, `constraint-dependencies`, `dev-dependencies`, etc.) are present.
- `requires-python = ">= 3.11"` (`pyproject.toml:9`) matches `uv.lock` `requires-python = ">=3.11"` (`uv.lock:3`) and the `--python 3.11` compile flag (`Makefile:50-51`).

## Q6: Where do Makefile and Justfile overlap or diverge in dependency-management recipes?

### Findings

**Overlap:**
- Both `sync` recipes run the identical install pair: `uv pip sync requirements-dev.txt` + `uv pip install -e .[test]` (`Makefile:45-47`; `Justfile:6-8`).
- Both provide `check`/`test`/`lint`/`format`/typecheck recipes over `deadcode`+`tests`.

**Divergence:**
- **Venv creation / Python pinning:** only the Makefile creates the venv (`uv venv -p $(PYTHON_VERSION) .venv`, `Makefile:10`) with `PYTHON_VERSION ?= 3.11` (`Makefile:3`) and bootstraps uv (`pip install uv`, `Makefile:9`). The Justfile has no `.venv` target, no `uv venv`, and no Python-version pin — it assumes a pre-existing environment and uses `uv run`.
- **Tool execution:** Makefile calls `.venv/bin/<tool>` directly; Justfile uses `uv run <tool>`.
- **Compilation:** `compile` exists only in the Makefile (`Makefile:49-51`); the Justfile cannot regenerate the requirements files.
- **`check` composition differs:** Makefile `check = test lint mypy audit deadcode` (`Makefile:5`) — includes `audit` (pip-audit) and `deadcode`. Justfile `check = check-format check-lint check-complexity check-typecheck test` (`Justfile:34`) — adds format-check and a dedicated `C901` complexity check, but omits `audit` and `deadcode`.
- **Extra recipes unique to the Justfile:** `lifecycle` (`Justfile:1-4`, runs `uv run lifecycle` in a loop) and the `check-*` granular recipes.
- **Extra recipes unique to the Makefile:** `publish` (`Makefile:15-18`), `audit` (`Makefile:42-43`), `deadcode` (`Makefile:32-33`), `fix`/`fixlint` (`Makefile:6,26-37`).

## Cross-Cutting Observations

- The repo uses the **pip-compatibility interface of uv** (`uv pip compile`/`uv pip sync`/`uv pip install`) plus `uv venv`/`uv run`, not uv's project workflow (`uv add`/`uv lock`/`uv sync`). The single source of dependency truth is `pyproject.toml`; pins are generated artifacts.
- **Two parallel lock artifacts coexist**: the compiled `requirements*.txt` (actually used for installs) and `uv.lock` (read only implicitly by `uv run`). Neither runner regenerates `uv.lock`; no recipe runs `uv lock`.
- `requirements.txt` (runtime) is generated but has **no consumer**; all installs use `requirements-dev.txt`.
- The custom `gitlab` index (`pyproject.toml:48-50`) governs resolution for both compile and lock.
- CI exercises only the Makefile (`make .venv` + `make check`), across Python 3.11–3.14 (`check.yml`).

## Open Areas

- **How/when `uv.lock` is regenerated** is not encoded anywhere (no `uv lock` recipe in Makefile/Justfile/CI). It appears hand-maintained relative to `requirements-dev.txt`; consistency between the two is not verified by any automated check.
- **No `.python-version` file** exists (glob found none); Python pinning is only via the Makefile `PYTHON_VERSION` variable and the `--python 3.11` compile flags.
- Whether `uv.lock` is ever actually consumed in practice: only implicitly by `uv run` in Justfile recipes; CI never invokes the Justfile.
