# Research Findings

## Q1: Where are runtime and dev/test dependencies declared, and what version constraints are specified in `pyproject.toml`?

### Findings
- **Runtime dependencies:** `dependencies = []` — the project has **no runtime
  dependencies** (`pyproject.toml:21`).
- **Dev/test dependencies:** declared under `[project.optional-dependencies]` as
  the `test` extra (`pyproject.toml:23-34`):
  `hatch, ruff, mypy, pip-audit, deadcode, pytest, pytest-cov, pytest-xdist, vupi`.
- **No version constraints** are pinned on any dependency — every entry is a bare
  package name with no `==`, `>=`, or `~=` specifier (`pyproject.toml:24-34`).
- Note the `test` extra lists `deadcode` itself (`pyproject.toml:29`), creating a
  self-referential dev dependency (reflected in `uv.lock:591` as
  `{ name = "deadcode", marker = "extra == 'test'" }`).
- Python floor: `requires-python = ">= 3.11"` (`pyproject.toml:9`); classifiers
  advertise 3.11–3.14 (`pyproject.toml:16-19`).
- Build backend: `hatchling` (`pyproject.toml:43-45`).

## Q2: How are `requirements.txt` / `requirements-dev.txt` generated, and what role does the `-U`/upgrade flag play?

### Findings
- Both files are generated by `uv pip compile` from `pyproject.toml`. Header
  comments record the originating command (`requirements.txt:1-2`,
  `requirements-dev.txt:1-2`).
- The regenerating recipe is the **Makefile `compile` target** (`Makefile:49-51`):
  ```
  uv pip compile -U -q pyproject.toml -o requirements.txt
  uv pip compile -U -q --all-extras pyproject.toml -o requirements-dev.txt
  ```
- `requirements.txt` compiles base deps only (empty body since runtime deps are
  empty — `requirements.txt` has only the 2 header lines).
- `requirements-dev.txt` uses `--all-extras`, so it includes the `test` extra and
  its full transitive closure, fully pinned with `==` and `# via` provenance
  comments (`requirements-dev.txt:3-289`).
- **`-U` flag:** `--upgrade`. It tells `uv pip compile` to ignore any previously
  pinned versions in the existing output file and re-resolve every dependency to
  the **latest** compatible versions. Without `-U`, uv prefers already-pinned
  versions. This is the mechanism by which "latest versions" enter the pinned
  files (`Makefile:50-51`).
- `-q` = quiet. There is **no Justfile equivalent** of `compile` — only the
  Makefile regenerates the requirements files.

## Q3: How is the dependency set locked and synced for dev and CI — relationship between `uv.lock`, the requirements files, and `uv pip sync` / `uv pip install`?

### Findings
- **Two parallel lock artifacts exist:**
  - `uv.lock` — full uv lockfile, `version = 1`, `revision = 3`,
    `requires-python = ">=3.11"` (`uv.lock:1-3`), with resolution-markers for
    3.14/3.15 and win32/non-win32 (`uv.lock:4-10`).
  - `requirements-dev.txt` — flat pinned export used for installing.
- **Sync is driven by the requirements file, not `uv.lock`.** Both build runners
  use the same two-step sync:
  - Justfile `sync` (`Justfile:6-8`):
    `uv pip sync requirements-dev.txt` then `uv pip install -e .[test]`.
  - Makefile `sync` (`Makefile:45-47`) and `.venv` bootstrap (`Makefile:8-12`):
    identical two steps.
- `uv pip sync requirements-dev.txt` makes the environment **exactly match** the
  pinned set (installs/removes to match). `uv pip install -e .[test]` then
  installs the local project in editable mode with the `test` extra.
- Every Justfile task (`test`, `format`, `lint`, `typecheck`, and all `check-*`)
  declares `sync` as a prerequisite, so the env is re-synced before each task
  (`Justfile:10-32`).
- **`uv.lock` is not directly referenced by any sync/install command** in the
  Justfile or Makefile. No `uv sync` (project-mode) command appears; only
  `uv pip sync` against the requirements export is used. `uv.lock` is maintained
  but installation flows through `requirements-dev.txt`.
- The `uv.lock` packages resolve from the custom gitlab index (see Q4), e.g.
  `source = { registry = "https://gitlab.com/api/v4/projects/niekas%2Fpackages/..." }`
  (`uv.lock:15`, repeated throughout).

## Q4: What custom/non-default package indexes are configured, and how do they affect resolution?

### Findings
- One custom index is declared (`pyproject.toml:48-50`):
  ```
  [[tool.uv.index]]
  name = "gitlab"
  url = "https://gitlab.com/api/v4/projects/niekas%2Fpackages/packages/pypi/simple"
  ```
- This is a GitLab PyPI package registry (project `niekas/packages`). In `uv.lock`
  every package's `source` is this gitlab registry rather than the default PyPI
  (`uv.lock:15`, `:25`, `:606`, `:615`, etc.), i.e. resolution is pinned to the
  gitlab index as the resolving registry.
- The actual wheel/sdist download `url`s in `uv.lock` still point at
  `files.pythonhosted.org` (e.g. `uv.lock:16-18`), indicating the gitlab index
  proxies/mirrors PyPI artifacts while serving the `simple` API used for version
  resolution.
- `[[tool.uv.index]]` is a uv-specific setting; it governs `uv pip compile`,
  `uv pip sync`, and `uv.lock` resolution. `pip-audit` (Makefile `audit`,
  `Makefile:42-43`) does not read this and uses its own defaults.

## Q5: How does CI install deps and run checks, and across which Python versions? How could a dependency upgrade interact with the version matrix and `requires-python`?

### Findings
- Workflow: `.github/workflows/check.yml`, name "Checks"
  (`.github/workflows/check.yml:1`). Triggers on push/PR to `main`
  (`check.yml:3-7`).
- Runs on `ubuntu-latest` (`check.yml:15`) with a matrix
  `python-version: ["3.11", "3.12", "3.13", "3.14"]` (`check.yml:17-19`).
- Steps (`check.yml:21-32`): checkout → `actions/setup-python@v5` with the matrix
  version → install via `make .venv PYTHON_VERSION=${{ matrix.python-version }}`
  → `make check`.
- `make .venv` (`Makefile:8-12`): `pip install uv`, `uv venv -p $(PYTHON_VERSION)
  .venv`, then `uv pip sync requirements-dev.txt` + `uv pip install -e .[test]`.
  `PYTHON_VERSION ?= 3.11` is the default (`Makefile:3`).
- `make check` runs `test lint mypy audit deadcode` (`Makefile:5`) — note this is
  the **Makefile** `check`, distinct from the **Justfile** `check`
  (`check-format check-lint check-complexity check-typecheck test`, `Justfile:34`).
  CI uses the Makefile path.
- **Interaction with the matrix / `requires-python`:**
  - `requirements-dev.txt` is a single flat pin set, but it is resolved with
    cross-version resolution-markers in `uv.lock` (`uv.lock:4-10`). A `-U` upgrade
    could raise a transitive package to a version whose own `requires-python`
    floor exceeds 3.11, which would break the 3.11 matrix leg during
    `uv pip sync`.
  - `mypy` config pins `python_version = "3.11"` (`pyproject.toml:165`); a
    type-checking dependency upgrade is validated against 3.11 semantics.
  - The matrix tests 3.11–3.14; the project's `requires-python = ">= 3.11"`
    (`pyproject.toml:9`) and `uv.lock` `requires-python = ">=3.11"` (`uv.lock:3`)
    must stay ≤ the lowest matrix entry (3.11) for all legs to install.
  - Some pinned packages already ship cp314 wheels (e.g. ast-serialize,
    `uv.lock` ast-serialize entry shows `cp314-cp314t` wheels), relevant for the
    3.14 leg.

## Q6: What tooling verifies dependency health/consistency, and how is it invoked?

### Findings
- **`pip-audit`** — declared in the `test` extra (`pyproject.toml:28`), pinned at
  `pip-audit==2.10.1` (`requirements-dev.txt:153`). Invoked by the Makefile
  `audit` target: `.venv/bin/pip-audit` (`Makefile:42-43`), and included in
  Makefile `check` (`Makefile:5`), which CI runs.
- **`uv pip sync`** enforces environment-vs-pin consistency (installs/removes to
  exactly match `requirements-dev.txt`) — Justfile/Makefile `sync`
  (`Justfile:6-8`, `Makefile:45-47`).
- **`uv pip compile -U`** (`Makefile:49-51`) regenerates pins; comparing the diff
  is the mechanism for surfacing upgrades.
- **Quality gates** bundled into checks:
  - Makefile `check` = `test lint mypy audit deadcode` (`Makefile:5`): pytest,
    ruff lint, mypy, pip-audit, and `deadcode` self-run (`Makefile:32-33`).
  - Justfile `check` = `check-format check-lint check-complexity check-typecheck
    test` (`Justfile:34`) — note the Justfile `check` does **not** include
    `audit`; pip-audit is only in the Makefile path.
- `make audit` runs `pip-audit` with no arguments, so it audits the currently
  installed environment (synced from `requirements-dev.txt`) against advisory
  databases. It does not consult `[[tool.uv.index]]`.

## Cross-Cutting Observations
- **Two redundant runner files** (Justfile and Makefile) provide overlapping
  recipes (`sync`, `test`, `lint`, `format`, `check`) but differ: only the
  Makefile has `compile` (regeneration) and `audit`; CI invokes the **Makefile**
  (`check.yml:29,32`), while `CLAUDE.md` instructs use of `just`.
- **No version constraints anywhere in `pyproject.toml`** — all version control
  lives in the generated lock/pin files (`requirements-dev.txt`, `uv.lock`).
  "Latest versions" is achieved by `uv pip compile -U`, not by spec ranges.
- **Dual lock artifacts** (`uv.lock` + `requirements-dev.txt`) can drift: installs
  use the requirements export, but `uv.lock` is a separately maintained full
  lockfile. Both currently target `requires-python >=3.11`.
- Custom **gitlab index** is the resolution source-of-record across `uv.lock`.

## Open Areas
- **Whether `uv.lock` is ever consumed**: no command in Justfile/Makefile/CI runs
  `uv sync` or otherwise reads `uv.lock`; it appears maintained (revision 3,
  freshly dated) but installation flows exclusively through
  `requirements-dev.txt`. How/when `uv.lock` is regenerated is not encoded in any
  recipe.
- **Authentication to the gitlab index** (tokens/credentials) is not configured in
  any tracked file examined; not determinable from the repo.
- `requirements.txt` (runtime) is effectively empty because runtime
  `dependencies = []`; its `compile` step exists but produces no pins.
