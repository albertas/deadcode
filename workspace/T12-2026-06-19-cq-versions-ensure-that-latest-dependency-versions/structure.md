# Structure Outline

## Approach

Upgrade every direct and transitive pin to its latest version compatible with
`requires-python >= 3.11` by **regenerating** the autogenerated artifacts via the
sanctioned `-U` flow (`make compile` → `uv pip compile -U`) plus a separate
`uv lock --upgrade` for `uv.lock` — never by hand-editing pins or adding
specifiers to `pyproject.toml`. Sign-off is the CI path: `make .venv && make check`
on Python 3.11 first, then the rest of the matrix.

**Slicing note:** there are no DB/service/API/UI layers here. "Vertical" is
interpreted as each phase producing one regenerated artifact (or one validation
surface) that is independently verifiable and valuable even if a later phase
fails. Phase order is foundation-first: prove tooling reachability → produce the
file installs actually consume → produce the secondary lockfile → widen version
coverage.

---

## Phase 1: Verify tooling + GitLab index reachability (foundation)

Confirm `uv` is present and the custom GitLab PyPI index resolves before touching
any artifact — the largest open risk (auth not in any tracked file). No file
changes; this is a precondition gate.

**Files**: none modified (read `pyproject.toml:48-50` for index config).
**Key commands / interfaces**:
- `uv --version` — tool present
- `uv pip compile -U -q --all-extras pyproject.toml -o /tmp/probe.txt` — dry probe
  against the `gitlab` index (`[[tool.uv.index]]`)

**Verify**: `uv --version` exits 0; the probe command exits 0 and `/tmp/probe.txt`
is non-empty with `==` pins. If it fails with an auth/401/403 error, STOP and
report — credentials must be supplied to the environment (per Open Risks); do not
proceed to Phase 2.

---

## Phase 2: Regenerate `requirements-dev.txt` and pass `make check` on 3.11

The core deliverable: bump every pin in the file installs actually consume, then
prove the exact CI default leg (3.11) installs and passes all gates including
`pip-audit`. Also regenerate `requirements.txt` (expected header-only).

**Files**: `requirements.txt`, `requirements-dev.txt` (regenerated);
possibly `pyproject.toml` *only* if a transitive `requires-python` floor conflict
forces a minimal constraint (Design Decision 4).
**Key commands / changes**:
- `make compile` — runs both `uv pip compile -U` invocations (`Makefile:49-51`)
- `make .venv PYTHON_VERSION=3.11` then `make check` (= `test lint mypy audit deadcode`)
- Conflict handler: if `uv pip sync` on 3.11 fails because a transitive package's
  `requires-python` > 3.11, add a minimal floor constraint on *that single package*
  and record the reason — do not raise the project floor or drop 3.11.

**Verify**:
- `make compile` exits 0; `git diff --stat requirements-dev.txt` shows pin bumps.
- `git diff requirements.txt` shows body still empty (header lines only) — assert
  no non-comment, non-blank lines: `grep -vE '^\s*(#|$)' requirements.txt` returns
  nothing.
- `make .venv PYTHON_VERSION=3.11 && make check` exits 0 (coverage ≥ 95%, ruff,
  mypy, pip-audit, deadcode all green).

---

## Phase 3: Regenerate `uv.lock` and confirm consistency

Bring the secondary lockfile up to the same upgraded resolution so the two
artifacts don't drift. `uv.lock` is not consumed by any recipe, so green CI does
not prove its consistency — regenerate and inspect explicitly.

**Files**: `uv.lock` (regenerated).
**Key commands / changes**:
- `uv lock --upgrade` (against same `pyproject.toml` + `gitlab` index)
- If `uv lock` is unavailable or auth-fails against the index: document `uv.lock`
  drift as a known gap and proceed (Design Decision 2) — Phase 2 remains valid.

**Verify**:
- `uv lock --upgrade` exits 0; `git diff --stat uv.lock` shows version bumps.
- `head -3 uv.lock` still shows `version = 1`, `requires-python = ">=3.11"`.
- Spot-check that key packages (`ruff`, `mypy`, `pip-audit`, `pytest`) show the
  same versions in `uv.lock` as in `requirements-dev.txt`:
  `grep -E 'name = "(ruff|mypy|pip-audit|pytest)"' -A1 uv.lock` versions match the
  `==` pins in `requirements-dev.txt`. Note any mismatch.

---

## Phase 4: Validate across the full Python matrix (3.12–3.14)

Mirror the remaining CI legs locally — the only pre-merge signal for non-3.11
versions, and where a transitive `requires-python` floor bump or missing cp3xx
wheel would surface.

**Files**: none (validation only); may loop back to Phase 2's conflict handler if
a leg fails.
**Key commands**:
- For each `V` in `3.12 3.13 3.14`: `make .venv PYTHON_VERSION=$V && make check`

**Verify**: each of the three runs exits 0. If any leg fails to install due to a
`requires-python` floor, return to Phase 2 (constrain the offending package,
recompile, re-run Phases 2–4). If a newer ruff/mypy fails lint/type checks, apply
surgical fixes confined to what the upgrade broke (Open Risks).

---

## Testing Checkpoints

After each phase the following should hold (useful if context resets mid-task):

1. **Phase 1**: `uv` present; GitLab index resolves (probe produces pins). If not,
   work is blocked on credentials — nothing downstream is valid.
2. **Phase 2**: `requirements-dev.txt` regenerated with bumped pins;
   `requirements.txt` body empty; `make check` green on 3.11. This alone delivers
   the headline goal (latest pins + passing default CI leg).
3. **Phase 3**: `uv.lock` regenerated and version-consistent with
   `requirements-dev.txt` for spot-checked packages (or drift documented).
4. **Phase 4**: `make check` green on 3.12, 3.13, 3.14 — full matrix parity with
   CI. Any added per-package floor constraint and any surgical code fix is recorded
   with its reason.

**Out of scope (do not do):** add specifiers/ranges to `pyproject.toml` (except a
forced minimal transitive floor), hand-pick versions, change `requires-python` /
matrix / mypy `python_version`, add a Justfile `compile`/`audit` recipe, touch
GitLab index config, or remove the self-referential `deadcode` dev dependency.
